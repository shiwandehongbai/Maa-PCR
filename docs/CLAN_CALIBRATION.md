# 公会战校准格式

## 能力与版本

生产校准只从安装目录的 `assets/resource/clan-battle-calibrations/index.json` 加载。Python 和 GUI 固定校验索引 SHA-256，再核对所选 profile 的摘要。玩家作业不能提供校准路径或“已验证”标志。

索引保留 `version` 和 `entries`。每项原有字段为 `calibration_id`、`server`、`content_version`、`frame_size`、`profile_path` 和 `profile_sha256`。同一服务器、内容版本及画面尺寸只能有一项。

索引版本 2 增加 `capabilities`，值为无重复的字符串数组：

| 值 | 用途 |
| --- | --- |
| `simulation` | 单次模拟。 |
| `timed` | 按剩余秒数切换 SET／AUTO，必须同时通过真实时序测量。 |
| `formal` | 正式普通挑战。 |
| `carryover` | 补偿挑战，同时要求 `formal`。 |

空数组不授予执行能力。实际战斗先检查对应模式；非空秒数轴还要求 `timed`。`timed` 不能单独作为战斗模式。

索引版本 1 只支持纯 AUTO 模拟。profile 版本 1 即使放入版本 2 索引，也不能声明 `timed`、`formal` 或 `carryover`。玩家作业和三刀请求继续使用原版本 1。

## 页面与材料

profile 保留既有页面、动作、编队、支援和保存帧字段。版本 2 另支持 `boss_targets`、`phase_labels`、`support_modes` 和 `daily`，具体页面约束由原生校准器校验。保存帧、模板和 profile 均须与索引摘要一致；路径必须留在安装目录内。模板列表的每一项都须单独绑定摘要。

`support_modes: ["none"]` 将执行范围限制为全部自有角色，并允许省略支援布局及相关动作。缺少这项明确声明时，仍要求完整支援校准。

版本 2 的全自有配置可在 `formation` 中声明 `star_source: "account_snapshot"`。此时星级来自作业绑定的账号快照 `battle_rarity`，不以已解锁的 `rarity` 替代，也不依赖编队卡片的星级／徽标动画。快照沿用账号资料的 24 小时有效期，账号、区服、内容版本、文件摘要和五个出战星级均须匹配；未知或不符时停止。GUI 与 Python 使用同一限制。画面仍逐次核对实际五人、支援标记、目标与模式；当前不支持用自有账号快照证明支援星级。

协议同步可能使游戏客户端断线，应在空闲时读取，再回到游戏核验账号。读取本身不修改角色星级；游戏中手动调整星级后，须重新同步并保存作业确认。

CP 字段接受明确的 `N / 900` 或同帧“已达今天的上限”文字；后者对应既有日上限 900。数字仍须在 0～900 内，不按进度条颜色或剩余次数猜数值。两种状态均保留页面守卫和 0.9 OCR 门限。

`daily` 的只读页面校准不能授予正式出刀资格。正式及补偿还要求完整的执行页面、动作、已用角色和补偿槽位校准；额外样本同样由安装内路径和摘要绑定。

批次在每次 `observe` 返回后取得校验时间，再检查真实 `observed_at`。这同时适用于首次观察和开战前复读。未来时间、超过 60 秒和跨日的观察仍须拒绝，不能为通过检查而回填较早的采集时间。

模拟难度页没有真实轮次时，读取结果使用 `round: null` 和 `round_source: selected_difficulty`，并附 `selected_difficulty` 的实际阶段、Boss 编号和模拟标记。三项均与当前目标匹配时，才接受这项结果。正式战仍核对实际轮次。

## 秒数轴与开场

声明 `timed` 的 profile 必须提供 `timing_measurements`，其中仅有安装内相对 `path` 和 `sha256`。文件摘要、JSON 格式及完整测量内容验证后，才交给原生执行器。测量文件使用既有 `owner_native_clan_timing` 类型，绑定校准编号和 HUD 版本。

测量必须覆盖完整 `full_read_tick` 观察和 `toggle_dispatch_and_full_team_readback` 输入读回。观察间隔、输入耗时及游戏秒时长各至少 20 条。`battle_speed` 必须是整数 1；观察间隔不超过 250 ms，输入读回不超过 500 ms。整组操作预算必须严格小于 1,000 ms 和最短实测游戏秒，两项取较小值。

执行轴时，每次观察和开关读回都必须确认 1 倍速。倍速未知或变化、漏秒、状态不明均停止，不补点。含秒数轴的版本 2 开场首帧须在起始秒数时，确认 SET／AUTO 已与作业一致。普通战斗为 90 秒，补偿使用执行器已核对的实际起始秒数；不能在战斗开始后补设，再把后来的正确设置记作开场成功。

## 无轴开场与倍速

版本 2 可提供 `auto_battle`，仅用于 `switches: []` 的单次模拟。必填字段为 `speeds`、`opening_guards`、`paused_guards`、`auto_on`、`auto_off`、`speed`、`set_badge`、`empty_tp` 和 `samples`，另允许可选的 `inheritance`。全部样本和模板沿用安装内路径与 SHA-256 绑定。

正式适配器编译管线前，先复制已校验的校准资料，再移除副本中的 `auto_battle`。正式战和补偿不能接入依赖“模拟战中”标记的暂停链，也不能修改共用校准。正式开场 SET／AUTO、继承及倍速仍需独立实机校准；这项隔离不授予正式执行能力。

`inheritance` 只含 `battle_selected`、`radio_on`、`radio_off` 和 `samples`。三个标记均为带摘要的模板；两个单选按钮使用实际 18×18 像素内部样本。读取时同时核对设定标题、已选战斗页、完整继承说明、两个单选项文字及互斥选中状态。滚动位置由同帧文字定位，不以固定屏幕高度推断状态。缺少这份资料的旧校准继续使用原手动准备方式。

继承变更沿用 `Journal` 的持久锁和追加记录。关闭前先写入原值；恢复后只有同帧状态读回一致才能结账。正常结算先保存伤害，再恢复原值及目标页。Stop 或未知时不补点；待恢复记录阻止其他账号接管，也不能绕过原战斗未决记录。

`speeds` 是去重的整数数组，必须包含 1，候选范围为 1、2、4；加速档还须分别提供战斗页面的 `speed_two` 或 `speed_four`。当前登记 1／2，4 倍控件样本不授予执行资格。菜单 `speed` 必须分别提供 `1`、`2`、`4` 的完整文字标记。

`opening_guards` 含三个原生同帧锚点。`paused_guards` 含菜单、模拟标记、时钟及零伤害四个锚点；第 3 项固定为有序的 90／89 秒模板和摘要列表。读取时必须只有一个时钟模板命中。`empty_tp` 逐槽偏移验证五人空 TP 条，任何填充 TP 像素均拒绝开场。暂停画面的五人身份、SET 边框和徽标、AUTO、速度及零伤害还须全部明确。

无轴设置只在暂停的 1:30 或 1:29、零伤害且五人 TP 为零时执行。每项输入绑定实际角色 ID 和前态，单次点击后核对全队，时间必须保持冻结。倍速与开关正确后恢复战斗，并再次读取实际 HUD。该独立暂停路径不放宽秒数轴的起始秒数和耗时门限。

GUI 模式文件保留版本 1 和可选整数 `battle_speed`。旧三字段配置仍按 1 倍读取；旧正式 1 倍配置可打开，但开始前必须重新核对并保存固定 2 倍。程序不自动改写旧文件。Python 版本 4 的 `clan_battle_speed` 仍只用于单次模拟；正式速度来自已核验的正式校准，不新增请求字段。作业、三刀计划和执行请求格式保持不变。

## 正式无轴开场与补偿

`daily.execution.opening` 提供独立的正式开场描述，`battle_speed` 必须为整数 2。它包含正式开场和暂停锚点、时钟区域、SET／AUTO、1／2 倍菜单与 2 倍 HUD 标记、五人空 TP、明确点击区域、继承和保存帧。保存帧必须恰好为 `battle`、`paused`、`battle_two` 各一份。模板、样本和依赖仍由安装内路径及 SHA-256 绑定；模拟的 `auto_battle` 不授予正式开场资格。可选 `start_seconds` 明确列出已覆盖的起始秒数；省略时只覆盖 90 秒。显式列表须非空、去重、由 1～90 的整数构成并包含 90，不能将普通 90 秒样本视为任意短补偿的证据。

正式和补偿只接受全自有、无战中切换作业。正式开场绑定保留的消费 intent、目标实例、队伍及消费模式，不能由动作参数覆盖。普通挑战使用已核验起始时间；补偿从实际库存及 `action.start_seconds` 取得起始秒数。首次及暂停读回须与该时间一致，逐项输入后暂停秒数须不变。不能套用模拟 90／89 秒模板；动画扣秒等未取样分支保持拒绝。

继承使用正式独立的 Journal 记录原值。准备和读回失败在消费 intent 前停止；真实结果与消费确认后先结账，再恢复原值。Stop、断线或状态未知时不追加恢复输入，待恢复记录只允许原账号在下一次明确 Start 中处理。

新增格式和离线回放不授予正式或补偿能力。两项能力分别等待完整页面、普通次数扣减、补偿发放与消费的真实证据；补偿目标必须是同编号 Boss 的已观察新实例。

格式检查和离线回放不代表实机验收。实际索引只登记已经审核的能力，正式次数与补偿消费仍须各自的真实验证。
