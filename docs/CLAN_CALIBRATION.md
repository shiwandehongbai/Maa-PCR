# 公会战校准格式

## 能力与版本

生产校准只从安装目录的 `assets/resource/clan-battle-calibrations/index.json` 加载。Python 和 GUI 固定校验索引 SHA-256，再核对所选 profile 的摘要。玩家作业不能提供校准路径或“已验证”标志。

索引保留 `version` 和 `entries`。每项原有字段为 `calibration_id`、`server`、`content_version`、`frame_size`、`profile_path` 和 `profile_sha256`。同一服务器、内容版本及画面尺寸只能有一项。

索引版本 2 增加 `capabilities`，值为无重复的字符串数组：

| 值 | 用途 |
| --- | --- |
| `simulation` | 单次模拟。 |
| `timed` | 按剩余秒数切换 SET／AUTO，必须同时通过真实时序测量。 |
| `formal` | 正式普通挑战。 |
| `carryover` | 补偿挑战，同时要求 `formal`。 |

空数组不授予执行能力。实际战斗先检查对应模式；非空秒数轴还要求 `timed`。`timed` 不能单独作为战斗模式。

能力登记不等于阶段验收名单。当前版本 2 索引条目没有阶段资格字段；国服 B 服内容版本 `202610141448` 已登记 `simulation`、`formal` 和 `carryover`。D5 → D4 → D1 三队已完成正常 GUI 自动模拟，均为全部自有、指定 SET、AUTO 开和 2 倍速。补偿候选仅覆盖全自有队伍和 1 条非空库存，库存数量不符时停止；`timed` 尚未登记，具体范围见[分项验收](CLAN_ACCEPTANCE.md)。

D5 普通正式挑战已通过正常 GUI 全程自动验收，伤害为 188,475,474。D4 自动完成战斗和 147,864,443 伤害读回，返回时因重复大厅读取失败停止；随后按原证据补记 `settled`，原 `stopped` 报告保留。三刀整批未连续全自动完成。

D1 已由正常 GUI 选齐五名 5 星角色，完成 Start、确认及首次暂停 88 秒读回。停止时 AUTO 开、2 倍速，SET 为 00000，尚未调整至 10110。同一 1:28 暂停页的重复 OCR 置信度不足，触发 `controls_unknown`。随后经授权人工恢复，造成 156,633,756 伤害并击杀目标；沿原 intent 追加 `settled`，保留人工介入标记和原 `stopped` 报告，不计该次 D1 自动全程通过。

自然发放的 49 秒补偿已通过正常 GUI 全程自动验收。程序使用全自有原阵容完成 Start、独立开始确认和开场暂停，将 SET 从 00000 按三处差异调整为 10110，保持 AUTO 开、2 倍速，恢复战斗并读回 118,305,835 伤害。结算后确认补偿库存为 0，并自动返回大厅；期间无人工游戏输入。

界面尚无续接已暂停战斗的入口。校准加载、离线回放和实机验收分别记录；此前程序外人工正式采样只记外部消费。

索引版本 1 只支持纯 AUTO 模拟。profile 版本 1 即使放入版本 2 索引，也不能声明 `timed`、`formal` 或 `carryover`。玩家作业和三刀请求继续使用原版本 1。

## 页面与材料

profile 保留既有页面、动作、编队、支援和保存帧字段。版本 2 另支持 `boss_targets`、`phase_labels`、`support_modes` 和 `daily`，具体页面约束由原生校准器校验。保存帧、模板和 profile 均须与索引摘要一致；路径必须留在安装目录内。模板列表的每一项都须单独绑定摘要。

`support_modes: ["none"]` 将执行范围限制为全部自有角色，并允许省略支援布局及相关动作。缺少这项明确声明时，仍要求完整支援校准。

编队空槽使用带摘要的多模板识别，统一阈值为 0.9。现有灰白空格和红底“未编组”模板继续保留；第五格另追加灰白边框变体，其他四格不变。新变体已通过真实保存帧正反例和 Python 校准检查；正常 GUI 编队和正式全程范围见[分项验收](CLAN_ACCEPTANCE.md)。空槽与角色头像同时命中时继续拒绝，不根据总战力或未识别到目标头像推断空槽。

版本 2 的全自有配置可在 `formation` 中声明 `star_source: "account_snapshot"`。此时星级来自作业绑定的账号快照 `battle_rarity`，不以已解锁的 `rarity` 替代，也不依赖编队卡片的星级／徽标动画。快照沿用账号资料的 24 小时有效期，账号、区服、内容版本、文件摘要和五个出战星级均须匹配；未知或不符时停止。GUI 与 Python 使用同一限制。画面仍逐次核对实际五人、支援标记、目标与模式；当前不支持用自有账号快照证明支援星级。

协议同步可能使游戏客户端断线，应在空闲时读取，再回到游戏核验账号。读取本身不修改角色星级；游戏中手动调整星级后，须重新同步并保存作业确认。

CP 字段接受明确的 `N / 900` 或同帧满上限文字；后者对应既有日上限 900。实际 OCR 中的“今天／今无”只按完整句 `已达今[天无]的上限` 兼容，检测和解析使用同一规则。数字仍须在 0～900 内，不按进度条颜色或剩余次数猜测。两种状态均保留页面守卫和 0.9 OCR 门限。

`daily` 的只读页面校准不能单独授予正式出刀资格。正式及补偿分别要求对应能力和完整执行校准；当前已登记 `formal` 和 `carryover`，补偿限全自有队伍和 1 条非空库存。已用角色来自当日已结算 Journal，不恢复个人记录前置；额外样本同样由安装内路径和摘要绑定。

普通 90 秒、全自有且实际补偿库存为空时，执行一次 `observe → prepare → execute`。同一有效 Owner、连接、账号和游戏日内，期间未发生消费、状态未知或重连时，可复用原库存收据及 `observed_at`。实际目标页核对 CP、次数、Boss 和阶段，编队末尾核对实际五人、星级及模式。

`prepared_at` 独立记录真实准备时刻，最终 Start 和首次暂停使用这个时刻的 60 秒时效。原库存收据及 `observed_at` 保持不变，不回填观察时间。未来时间、跨日或绑定失效仍拒绝；补偿、非空库存和支援继续沿用原规则。

模拟难度页没有真实轮次时，读取结果使用 `round: null` 和 `round_source: selected_difficulty`，并附 `selected_difficulty` 的实际阶段、Boss 编号和模拟标记。三项均与当前目标匹配时，才接受这项结果。正式战仍核对实际轮次。

## 秒数轴与开场

声明 `timed` 的 profile 必须提供 `timing_measurements`，其中仅有安装内相对 `path` 和 `sha256`。文件摘要、JSON 格式及完整测量内容验证后，才交给原生执行器。测量文件使用既有 `owner_native_clan_timing` 类型，绑定校准编号和 HUD 版本。

测量必须覆盖完整 `full_read_tick` 观察和 `toggle_dispatch_and_full_team_readback` 输入读回。观察间隔、输入耗时及游戏秒时长各至少 20 条。`battle_speed` 必须是整数 1；观察间隔不超过 250 ms，输入读回不超过 500 ms。整组操作预算必须严格小于 1,000 ms 和最短实测游戏秒，两项取较小值。

本节的起始秒数与耗时要求仅适用于非空 `switches` 的秒数轴，当前仍未开放。执行轴时，每次观察和开关读回均须确认 1 倍速；倍速未知或变化、漏秒、状态不明时停止，不补点。普通 90 秒挑战和模拟的无轴作业使用下一节的实际暂停秒数和受影响角色首次 UB 条件，不要求开场首帧 SET／AUTO 已符合，也没有统一两秒期限。

## 无轴开场与倍速

版本 2 可提供 `auto_battle`，仅用于 `switches: []` 的单次模拟。必填字段为 `speeds`、`opening_guards`、`paused_guards`、`auto_on`、`auto_off`、`speed`、`set_badge` 和 `samples`，另允许可选的 `inheritance` 及兼容旧格式的 `empty_tp`。全部样本和模板沿用安装内路径与 SHA-256 绑定。

正式适配器编译管线前，先复制已校验的校准资料，再移除副本中的 `auto_battle`。正式战和补偿不能接入依赖“模拟战中”标记的暂停链，也不能修改共用校准。正式普通挑战已有独立开场样本；补偿流程按后文规则执行，不能由普通样本推定补偿已验收。这项隔离不代表正常 GUI 全程验收通过。

`inheritance` 必填字段为 `battle_selected`、`radio_on`、`radio_off` 和 `samples`，另允许可选的 `ub_auto_clear`。三个必填标记均为带摘要的模板；两个单选按钮使用实际 18×18 像素内部样本。读取时同时核对设定标题、已选战斗页、完整说明、两个单选项文字及互斥选中状态。滚动位置由同帧文字定位，不以固定屏幕高度推断状态。

`ub_auto_clear` 只含 `description`、`on_label` 和 `off_label` 三个 OCR 标记，用于只读“发动连结爆发时解除连结爆发立即发动模式”。读取复用已校准的互斥单选模板及保存帧。旧 profile 可省略此项。例行账号核对不再进入设置页读取此项，策略默认为未知，不阻断全匹配。可选读取仅观察当前页，不打开、切页、展开或关闭设置；未知不提供首次 UB 历史证明，也不修改选项。继承资料继续用于旧待恢复项，正常战斗保留继承值。

正常流程不临时关闭或恢复继承，也不新增相应 intent。旧 `Journal` 沿用持久锁和追加记录：同账号明确 Start 后，只有真实现值已等于旧记录原值，才能凭读回结账；冲突时保留待恢复项，不覆盖用户选择。待恢复记录阻止其他账号接管，原战斗未决仍先阻断。Stop 或未知时不追加输入。

`speeds` 是去重的整数数组，必须包含 1，候选范围为 1、2、4；加速档还须分别提供战斗页面的 `speed_two` 或 `speed_four`。当前登记 1／2，4 倍控件样本不授予执行资格。菜单 `speed` 必须分别提供 `1`、`2`、`4` 的完整文字标记。

`opening_guards` 含可操作菜单、模拟标记和动态时钟三个同帧锚点。当前 `paused_guards` 含主菜单文字、暂停模拟标记和时钟三个锚点；第 3 项使用 OCR。两端仍可读取旧四项守卫、90／89 秒双模板和 `empty_tp` 字段，但零伤害、空 TP 与固定两秒窗口不再作为无轴开场前置。暂停画面的五人身份、目标、模式、SET 边框与徽标、AUTO 和速度仍须全部明确。

普通 90 秒挑战和模拟在首次暂停时读取大于 0 且不超过名义起始秒数的实际秒数 P，并在本次开战内冻结 P。设置已匹配时不切换；有差异时，仅受影响角色需要首次 UB 尚未发生的可信证据，AUTO 或倍速变化会影响全队。每次输入绑定实际角色 ID 和前态，随后读回全队及冻结时间，再恢复战斗并核对 HUD。普通攻击伤害和 TP 增长均不能单独判为失败。秒数轴继续使用原起始秒数和耗时门限。

首次 UB 证据属于本次执行状态，不能由作业或校准 profile 提供一个“已验证”标志。首次可信账号仍实际核对一次，同一有效 Owner 跨槽复用；这一步不再调用可选 UB 策略读取。默认策略未知。只有显式取得当前页的真实读回，才能绑定玩家 ID、Owner 和有效连接；来源失效时不能继续使用旧策略。

标准 90 秒普通挑战和模拟在 1:24 之前不会首次 UB。首次暂停读到 85～90 秒时，可按已确认规则生成本次开战证据，同时核对 Owner、模拟／普通模式、90 秒名义起始时间、原生同帧读回及开战 token。1:24 及之后、短补偿不套用这项规则。

另一条条件性证明要求开战前可信读到 `auto_release_on_ub=false`、绑定仍有效，且本次 `CBStart` 至首次暂停未发送 UB 或控制输入。首个暂停中 AUTO 关闭及对应角色 SET 关闭时，才据此证明该角色尚未首次 UB。证据绑定本次开战 token、原生读回和初始帧，暂停期间保持不变。策略未知、失效或相关初态已开启时不能使用这条证明；缺少其他可信来源便停止。设置全匹配时不需要首次 UB 历史证明。

D5、D4 和 D1 的正常 GUI 模拟已验证当前保留继承和指定开场设置的流程。正式普通挑战、补偿及后续修正按各自证据记录，不能用模拟结果或离线夹具代替正式全程验收。

`read_battle_settings` 已在暂停且未取得读回收据时复用既有有界等待，最长 5 秒，0.9 识别门限不变。391 项相关检查和 3 张真实保存帧回放均退出 0。本次正常 GUI 补偿已执行这条暂停读回路径，完成三次 SET 调整及恢复；实机首次读回即成功，延迟恢复边界由保存帧回放验证。

GUI 模式文件保留版本 1 和可选整数 `battle_speed`。旧三字段配置仍按 1 倍读取；旧正式 1 倍配置可打开，但开始前必须重新核对并保存固定 2 倍。程序不自动改写旧文件。Python 版本 4 的 `clan_battle_speed` 仍只用于单次模拟；正式速度来自已核验的正式校准，不新增请求字段。作业、三刀计划和执行请求格式保持不变。

## 正式无轴开场与补偿

`daily.execution.opening` 提供独立的正式开场描述，`battle_speed` 必须为整数 2。它包含正式开场和暂停锚点、时钟区域、SET／AUTO、1／2 倍菜单与 2 倍 HUD 标记、明确点击区域、继承和保存帧；`empty_tp` 仅作旧格式兼容，可省略。保存帧必须恰好为 `battle`、`paused`、`battle_two` 各一份。模板、样本和依赖仍由安装内路径及 SHA-256 绑定；模拟的 `auto_battle` 不授予正式开场资格。可选 `start_seconds` 保留既有格式校验：显式列表须非空、去重，由 1～90 的整数构成并包含 90。补偿新流程不以该列表设置开场时间门槛；实际起始秒数仍来自游戏库存，本次 49 秒全自有单库存补偿已通过正常 GUI 全程验收。

`daily.execution.start_confirmation` 描述普通确认窗，可选的 `carry_start_confirmation` 描述独立补偿确认窗。两者分别要求 3 个标签、确认目标和对应页面名的样本，沿用安装内路径与摘要校验；实际消费模式决定使用哪个确认窗。

正式和补偿只接受全自有、无战中切换作业。正式开场绑定保留的消费 intent、目标实例、队伍及消费模式，不能由动作参数覆盖。普通挑战继续核对首次暂停秒数、首次 UB 证据及逐项输入后的读回。补偿从实际库存及 `action.start_seconds` 取得起始秒数，不套用模拟固定 90／89 秒模板。

补偿流程已通过本次全自有、单库存的正常 GUI 全程验收。程序使用同一 Boss 和原阵容，开场暂停、调整 SET、恢复并打完，不设置补偿开场时间或首次 UB 证明门槛。Boss 不可打或队伍不符时停止并交回玩家，不自动更换目标。后续执行仍须核对实际库存、队伍、Owner、目标实例和对应消费授权。

正式继承沿用独立 Journal 兼容旧记录，不再每刀临时关闭再恢复。旧待恢复项先核对原账号及当前实值，冲突时在消费 intent 前停止；真实结果与消费确认后先结账再返回。Stop、断线或状态未知时不追加输入。

能力以安装内已核验索引为准，当前登记 `formal` 和 `carryover`。D5 普通单场及本次补偿已全程自动通过；D4 保留恢复结账记录，D1 保留人工恢复标记。补偿仅覆盖全自有队伍和 1 条非空库存，数量不符时停止。后续消费须重新核对库存、绑定队伍和同一 Boss 的可挑战实例，并取得对应授权。

格式检查和离线回放不能代替实机验收。本次必要的正常 GUI 实机验收已完成，包含匹配运行包、源码和说明的开发候选 ZIP 已于 2026-10-28 交付。当前交付状态与后续安排见[正式战交接说明](CLAN_FORMAL_HANDOFF.md)。
