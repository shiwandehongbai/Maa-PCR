自然发放的 49 秒补偿已通过正常 GUI 全程自动验收。程序使用全自有原阵容完成 Start、独立开始确认和开场暂停，将 SET 从 00000 按三处差异调整为 10110，保持 AUTO 开、2 倍速，恢复战斗并读回 118,305,835 伤害。结算后确认补偿库存为 0，并自动返回大厅；期间无人工游戏输入。

## 导入和保存

界面按账号、作业、五人核对和三刀计划排列。账号资料窗口显示资料摘要、“刷新资料”和“使用资料并返回”；读取中显示停止。导入、清空、手填和原始字段放在高级资料中。刷新成功会保存缓存，复用资料不会更新采集时间，打开窗口不会自动登录。

1. 切换到“公会战”，核对渠道设置。当前接受 B 站账号资料。
2. 粘贴完整 B 站视频链接并获取，或打开已生成的 `bundle.json`。按分 P、套餐和队伍选择作业。
3. 对照完整原图和队伍局部图，核对期次、阶段、周目、Boss、五人形态、出战星级、SET、AUTO 与支援。不确定的字段须明确填写，识别候选不会自动确认。
4. 选择账号资料，点击“核对五人和操作并保存”。练度、EX 和强化差异只作提醒。修改作业或更换账号后需要重新确认。

B 站网页链接可带常见附加参数。明确的 `p` 参数会保留，未指定时获取全部分 P；获取状态显示在按钮旁。若返回 HTTP 412，可稍后重试或导入已有作业包，并核对采集日期。

当前只开放全部自有。出战星级来自已绑定资料的 `battle_rarity`，资料有效期为 24 小时；解锁星级 `rarity` 不能替代出战星级。星级留空时使用原账号缓存实值，不能据此保证符合作者设置。游戏内手动改星后须重新同步并保存确认；同步可能使客户端断线，重新进入后再开始。

换用资料时保留当前编辑，使旧作业和三刀确认失效。账号缓存已保存不等于作业已确认。每期材料单独保存，原图、BV、分 P、CID、时间点及摘要随作业保留。`agent-guide-review.json` 只保存当前选择，账号、角色目录和公开攻略库继续共用原目录。

命令行导入使用工程现有 Python：

~~~powershell
python -X utf8 -B scripts/prepare-clan-guide.py --video-url 'https://www.bilibili.com/video/BV1Rbh86XEsq/' --output '.runtime/clan-video-new'
~~~

输出目录必须尚不存在。默认获取全部分 P；`--page 2` 只处理指定分 P。获取失败会保留材料和错误，不覆盖已有作业。

## 单次模拟与开场设置

“单次模拟”可选择 1 或 2 倍速，一次 Start 只安排当前队伍的一次模拟。程序核对实际账号、期次、阶段、Boss 和“模拟战”标记；正式战另核对真实轮次。页面未知时停止。

程序保留游戏的 SET、AUTO 和速度继承，进战后读取实际状态，已匹配时直接使用。需要调整时先暂停，只修改与作业不符的项；每次操作后读回五人、开关和冻结的暂停秒数，恢复后再核对 HUD。

普通 90 秒挑战和模拟的调整须在受影响角色首次 UB 前完成。标准 90 秒普通挑战和模拟在 1:24 之前不会首次 UB；同一有效 Owner 的首次暂停读到 85～90 秒时，可按已确认规则核验。1:24 及之后、短补偿不套用。没有统一两秒、零伤害或零 TP 前置。

同一有效 Owner／设备连接实际核对一次玩家 ID，连续槽位复用绑定；切号、重连或绑定失效后重核。正常流程不增加每刀简介、个人记录或继承页检查。可选 UB 自动解除策略只读取当前设置页，默认未知，不阻断设置全匹配的路径。

停止、断线或页面未知后不继续输入。旧继承待恢复记录保留；原账号明确 Start 后，真实现值已等于记录原值才凭读回结账，冲突时停止，不覆盖用户接管后的选择。原战斗结果未决时先阻断，不为恢复设置重开战斗。

伤害和设置读回可信后，先写 Journal，再返回目标页。返回失败保留已知伤害并停止；未知结果不清账或自动重试。会战记录使用独立业务账本，不套用其他模式的每关次数。实际伤害不要求等于作者参考值。

## 三刀计划与正式挑战

在“核对五人和操作并保存”下方设置三刀目标，将已核对队伍依次设为第 1、2、3 刀。可以先保存部分目标，凑齐后点击“核对完整三刀预设”。三队须属于同一服务器、账号和期次；重复占用的自有角色会逐项提示，完整核对会停止，程序不替换角色。

`clan-battle-daily-plan.json` 保存作业引用及核对摘要。原图、作业、账号资料或确认变化后，需要重新核对相应目标。预设不保存已出次数或补偿库存，也不随 05:00 清除作业模板。

点击“载入第 N 刀到当前模拟队”可恢复该槽位已核对的队伍。程序复核原件、资料有效期、确认及文件版本，按预期摘要保存，写后读回成功才更新面板。其他队伍的保存确认继续保留。资料过期、原件变化或并发修改会拒绝载入；写后读回失败会取消面板确认，需重新打开核对。

模拟模式只执行当前队伍一次。正式模式使用独立开场和固定 2 倍速。旧正式 1 倍配置可读，开始前须重新核对并保存 2 倍；作业、三刀计划和执行请求格式保持 version 1。

普通 90 秒、全自有且实际补偿库存为空时，只走一次 `observe → prepare → execute`。同一有效 Owner、连接、账号和游戏日内，期间未发生消费、状态未知或重连时，复用原库存收据及 `observed_at`。实际目标页仍核对 CP、次数、Boss 和阶段，编队末尾核对实际五人、星级及模式。

真实准备时刻另记为 `prepared_at`，最终 Start 和首次暂停按它核验 60 秒时效，不改写原库存观察时间。补偿、非空库存和支援仍沿用原规则。普通单次编队已在 D1 正常 GUI 中完成选人及开战；后续由人工恢复收尾，不计该次 D1 自动全程通过。

正式开始前，程序读取账号、游戏日、CP、普通次数、补偿库存和具体 Boss 实例。消费前须明确当前目标及消费次数，并取得对应授权。旧现场值和旧 Owner 许可不能用于新一轮消费。

正式批次使用独立 Journal，绑定账号、期次、游戏日、三目标和确认摘要。同日已有消费意图后不能任意更换计划；已结算不重复，未知开战或结果不重发。程序外人工出刀经事实确认后单列外部消费。已有 intent 的人工恢复沿原记录结账并保留人工介入标记，不计作自动验收。

当前 CP 按累计进度读取，不能按每次开战扣减 300 核账。普通挑战每日最多 3 次，次数与 CP 按游戏 05:00 日界处理；实际可用次数始终以现场读回为准。补偿时间挑战另行记录，不能当作新增普通次数。历史活动规则见[国服官方团队战公告](https://www.bilibili.com/opus/1158728918930292785)。

## 补偿、支援和秒数轴

补偿只依据游戏实际发放的库存，绑定来源主刀、原队伍和同一 Boss 的可挑战实例。本次 49 秒补偿已完整自动执行并结算，收尾库存为 0。普通次数确认为 0 且仍有补偿时，按已有策略提示未用补偿。

补偿流程已通过本次全自有、单库存的正常 GUI 全程验收。程序使用同一 Boss 和原阵容，开场暂停、调整 SET、恢复并打完，不设置补偿开场时间或首次 UB 证明门槛。Boss 不可打或队伍不符时停止并交回玩家，不自动更换目标。后续执行仍须核对实际库存、队伍、Owner、目标实例和对应消费授权。

短补偿按真实库存起始秒数处理，不套用普通 90 秒的首次 UB 规则，不按击杀或余时公式生成，也不自动裁剪完整秒数轴。当前索引已登记 `carryover`，本次全自有、单条 49 秒库存已通过正常 GUI 全程自动验收。

支援接口保留“全部自有”“缺谁借谁（qsjs）”和指定支援的配置语义。部分账号缓存中的未知持有不能当作缺少。当前支援身份尚未完成校准，执行范围仍限制为全部自有。

纯 AUTO 作业的秒数轴留空。以下仅说明保留的格式，当前未开放执行：

~~~text
80 | 不变 | 100101=关；100201=开
59 | 关 |
~~~

第一列是剩余秒数，第二列是 AUTO（不变、开、关），第三列是角色编号或完整角色名及 SET 状态。秒数严格递减，同秒多项操作写在同一行。漏秒、未知状态、6002 断线或 Stop 后不补点；缺少读取间隔和整组操作耗时证据的轴不可执行。

## 校准与交付

校准只从安装内固定清单加载，Python 和 GUI 共同核对索引、profile、模板和样本摘要。玩家作业不能指定校准路径或标记“已验证”。格式见[公会战校准格式](CLAN_CALIBRATION.md)。

第五格灰白空槽变体已通过真实保存帧正反例及 Python 校准检查。正常 GUI 编队和正式战斗进度按顶部范围记录，离线回放不能代替完整实机验收。

`read_battle_settings` 已在暂停且未取得读回收据时复用既有有界等待，最长 5 秒，0.9 识别门限不变。391 项相关检查和 3 张真实保存帧回放均退出 0。本次正常 GUI 补偿已执行这条暂停读回路径，完成三次 SET 调整及恢复；实机首次读回即成功，延迟恢复边界由保存帧回放验证。

本次必要的正常 GUI 实机验收已完成，包含匹配运行包、源码及验收说明的开发候选 ZIP 已于 2026-10-28 交付。后续实际使用时优先观察普通三刀连续自动执行，安排见[正式战交接说明](CLAN_FORMAL_HANDOFF.md)。保留 D5 普通正式和本次补偿的通过范围，以及 D4、D1 的恢复记录。公开包排除账号资料、凭据、真实账本、原始游戏画面和开发绑定；该独立候选交付未覆盖常用安装，也未公开发布。后续本地源码合并的检查另记，不改变此 ZIP 的源码与验收范围。
